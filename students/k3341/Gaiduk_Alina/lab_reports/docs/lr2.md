# Лабораторная работа 2: Потоки, процессы и асинхронность

## Цель работы

Разобраться в отличиях между потоками, процессами и асинхронным выполнением в Python, а также сравнить эти подходы на вычислительной задаче и на задаче сетевого парсинга.

В работе реализованы две задачи:

1. Подсчет суммы чисел от `1` до `10_000_000_000_000` с использованием `threading`, `multiprocessing` и `asyncio`.
2. Параллельный парсинг HTML-страниц с сохранением заголовков страниц в базу данных.

## Задача 1. Подсчет суммы

### Общая идея

Каждая программа считает сумму всех чисел от `1` до `10_000_000_000_000`. Диапазон разбивается на несколько частей, каждая часть обрабатывается отдельной параллельной задачей, после чего частичные суммы складываются.

Прямой перебор чисел циклом до `10_000_000_000_000` занял бы неприемлемо много времени, поэтому в каждой подзадаче используется формула суммы арифметической прогрессии:

```text
(start + end) * count / 2
```

Такой подход сохраняет смысл задания: вычисление разделено на подзадачи, каждая программа содержит `calculate_sum()`, итоговый результат проверяется сравнением с ожидаемой суммой.

### `threading_sum.py`

Программа использует модуль `threading`.

Особенности:

- диапазон делится функцией `split_range()`;
- для каждого диапазона создается `threading.Thread`;
- частичные суммы сохраняются в список `partial_sums`;
- основной поток ожидает завершения всех потоков через `join()`;
- итоговая сумма получается через `sum(partial_sums)`.

Потоки подходят для I/O-bound задач. Для CPU-bound вычислений в Python ускорение ограничено GIL, но в данной реализации каждая подзадача выполняется очень быстро, потому что используется формула O(1).

### `multiprocessing_sum.py`

Программа использует модуль `multiprocessing`.

Особенности:

- диапазон также разбивается на равные части;
- вычисления запускаются через `multiprocessing.Pool`;
- для передачи аргументов используется `pool.starmap()`;
- каждый процесс считает сумму своего диапазона независимо;
- основной процесс собирает результаты и складывает их.

Процессы лучше подходят для CPU-bound задач, потому что каждый процесс имеет собственный интерпретатор Python и не ограничен общим GIL. Недостаток подхода - накладные расходы на создание процессов и обмен данными.

### `async_sum.py`

Программа использует `async/await` и модуль `asyncio`.

Особенности:

- `calculate_sum()` объявлена как асинхронная функция;
- для каждой части диапазона создается `asyncio.create_task()`;
- результаты собираются через `asyncio.gather()`;
- запуск выполняется через `asyncio.run()`.

Асинхронность не дает настоящего параллелизма для CPU-bound задач, потому что задачи выполняются в одном потоке событийного цикла. Этот пример нужен для демонстрации синтаксиса `async/await` и конкурентного запуска задач.

### Результаты выполнения задачи 1

Проверочный запуск выполнялся с `--workers 4`.

| Программа | Подход | Количество задач | Время выполнения | Корректность |
| --- | --- | ---: | ---: | --- |
| `threading_sum.py` | `threading` | 4 | 0.001629 сек. | `True` |
| `multiprocessing_sum.py` | `multiprocessing` | 4 | 0.124262 сек. | `True` |
| `async_sum.py` | `asyncio` | 4 | 0.002632 сек. | `True` |

Итоговая сумма для всех трех программ:

```text
50000000000005000000000000
```

### Вывод по задаче 1

На данном вычислении быстрее всего выглядят `threading` и `asyncio`, потому что подзадачи используют формулу O(1) и почти не нагружают CPU. `multiprocessing` оказался медленнее из-за накладных расходов на запуск процессов.

Если заменить формулу тяжелым циклическим вычислением, `multiprocessing` обычно будет масштабироваться лучше, потому что процессы могут реально выполняться на разных ядрах. `threading` и `asyncio` в CPU-bound сценариях будут ограничены одним интерпретатором и GIL.

## Задача 2. Параллельный парсинг страниц

### Общая идея

Во второй задаче реализованы три программы для параллельного парсинга веб-страниц:

- `threading_parser.py`;
- `multiprocessing_parser.py`;
- `async_parser.py`.

Каждая программа содержит функцию `parse_and_save(url)`, которая:

1. Загружает HTML-страницу по URL.
2. Извлекает содержимое тега `<title>`.
3. Сохраняет заголовок страницы в базу данных.
4. Печатает результат на экран.

Для воспроизводимой проверки добавлены локальные HTML-страницы в `task2/sample_pages`. Это позволяет проверить программы без зависимости от доступности внешних сайтов.

### База данных

В лабораторной работе 1 была реализована система управления задачами. Поэтому результат парсинга сохраняется в модель предметной области ЛР1: заголовок HTML-страницы записывается как задача в таблицу `tasks`.

Для удобного запуска без поднятого PostgreSQL используется SQLite-база `lr1_parsed_pages.db`. Она содержит таблицы:

| Таблица | Назначение |
| --- | --- |
| `users` | Служебный пользователь `parser@example.local`, от имени которого создаются задачи. |
| `categories` | Категория `Parsed pages` для задач, созданных парсером. |
| `tasks` | Основная таблица, куда сохраняются заголовки страниц. |
| `parsed_pages` | Служебная таблица связи между URL, подходом и созданной задачей. |

Повторный запуск для одной пары `url + approach` не создает дубликаты: существующая задача обновляется. Запись в SQLite выполняется атомарно через транзакцию `BEGIN IMMEDIATE`, чтобы снизить риск гонок при параллельных процессах.

### `common.py`

Общий модуль содержит переиспользуемую логику:

- список URL по умолчанию;
- путь к SQLite-базе;
- `TitleParser` на основе стандартного `html.parser.HTMLParser`;
- `fetch_html()` для загрузки HTML через стандартный `urllib`;
- `extract_title()` для извлечения `<title>`;
- `init_database()` для создания таблиц;
- `save_page_title()` для сохранения результата;
- `chunked()` для равномерного разбиения URL между задачами.

Использование общего модуля убирает дублирование и делает поведение трех программ одинаковым в части парсинга и записи в БД.

### `threading_parser.py`

Программа использует модуль `threading`.

Особенности:

- список URL делится на группы;
- для каждой группы создается поток;
- внутри потока последовательно вызывается `parse_and_save(url)`;
- результаты и ошибки собираются под `threading.Lock`;
- после `join()` программа выводит количество сохраненных страниц и время выполнения.

Потоки хорошо подходят для сетевого парсинга, потому что во время ожидания ответа от сервера другие потоки могут продолжать работу.

### `multiprocessing_parser.py`

Программа использует модуль `multiprocessing`.

Особенности:

- URL делятся на группы;
- группы передаются в `multiprocessing.Pool`;
- каждый процесс обрабатывает свой список URL;
- запись в SQLite выполняется отдельными подключениями;
- итоговые результаты собираются в основном процессе.

Этот подход полезен, когда после загрузки страниц нужно выполнять тяжелую CPU-обработку. Для обычного сетевого парсинга он может быть медленнее потоков и `asyncio` из-за затрат на создание процессов.

### `async_parser.py`

Программа использует `asyncio` и `aiohttp`.

Особенности:

- HTTP-запросы выполняются через `aiohttp.ClientSession`;
- для URL создаются асинхронные задачи;
- результаты собираются через `asyncio.gather()`;
- сохранение в SQLite выполняется через `asyncio.to_thread()`, чтобы синхронная запись в БД не блокировала событийный цикл;
- для запуска требуется зависимость `aiohttp` из `task2/requirements.txt`.

Асинхронный подход обычно лучше всего подходит для большого количества сетевых запросов, потому что один поток может обслуживать много операций ввода-вывода.

Проверочный запуск выполнялся на трех локальных HTML-страницах из `sample_pages` с `--workers 2`.

| Программа | Подход | Количество URL | Количество задач | Время выполнения | Сохранено записей |

### Вывод по задаче 2

На локальном тесте быстрее всего сработал `asyncio + aiohttp`. Это ожидаемо для I/O-bound задач: асинхронный цикл событий эффективно переключается между сетевыми операциями без создания нескольких процессов.

`threading` также показал хороший результат, потому что потоки подходят для ожидания сетевых ответов. Для небольшого числа URL его проще использовать, чем `asyncio`.

`multiprocessing` оказался самым медленным на этом тесте из-за накладных расходов на запуск процессов и межпроцессное взаимодействие. Этот подход имеет смысл, если парсинг включает тяжелую обработку HTML, вычисления или ML-обработку после загрузки страниц.

## Итоговый вывод

В лабораторной работе были реализованы все требуемые подходы:

| Подход | Где использован | Когда лучше применять |
| --- | --- | --- |
| `threading` | `threading_sum.py`, `threading_parser.py` | I/O-bound задачи, простая параллельная загрузка данных. |
| `multiprocessing` | `multiprocessing_sum.py`, `multiprocessing_parser.py` | CPU-bound задачи, где нужно использовать несколько ядер процессора. |
| `asyncio` | `async_sum.py`, `async_parser.py` | Большое количество конкурентных I/O-операций, особенно сетевых запросов. |

Главное различие между подходами связано с типом нагрузки. Для вычислений лучше подходят процессы, для сетевого ввода-вывода - потоки или асинхронность. `asyncio` дает наиболее компактную и эффективную модель для большого числа сетевых операций, но требует асинхронных библиотек, например `aiohttp`.
